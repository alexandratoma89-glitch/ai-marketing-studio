## What must be configured personally

1. **Meta first:** open https://developers.facebook.com/apps/ and sign in with the Facebook account that has full control of the Divine Work Page. Select the existing app if there is one; otherwise create an app for the Instagram/Facebook API use case. Meta changes labels, so choose Instagram API with Instagram Login for Instagram, and the appropriate Facebook Login business use case for Page access. Do not assume the two login methods use interchangeable app credentials.
2. **Instagram:** follow `docs/instagram-setup.md`, including migration `202610160004_instagram.sql`. Its exact callback is `https://www.thedivinework.com/api/studio/instagram/callback`. Required server variables remain `INSTAGRAM_APP_ID`, `INSTAGRAM_APP_SECRET`, `INSTAGRAM_TOKEN_ENCRYPTION_KEY`, `INSTAGRAM_EXPECTED_USERNAME=divinework.store`, `INSTAGRAM_DATABASE_READY=true`. Keep `INSTAGRAM_PUBLISHING_ENABLED=false`. Only a completed real OAuth grant confirms authorization; publishing remains separately unverified and source-locked.
3. **Facebook Page:** obtain the numeric Page ID from Page settings/about/transparency for the actual `@divinework.store` Page. The handle alone is not enough. Add `https://www.thedivinework.com/api/studio/social/facebook/callback` as a valid redirect URI in the Facebook Login setup. Server variables are `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` and `FACEBOOK_PAGE_ID`. The owner must be able to grant `pages_show_list` and `pages_read_engagement`. The code checks the granted scopes, selects that exact numeric Page ID and verifies a content-management task. Graph API v24.0 is used. No `pages_manage_posts` scope is requested in this phase. Future Page publication needs separate implementation and permission approval.
4. **Supabase:** apply the supplied `supabase/migrations/202610270006_social_connections.sql` once through SQL Editor. It is independent of the existing video/bookings tables and stores only these new connections and temporary states. It grants RPC execution to `service_role`, enables RLS and does not expose tokens to browser roles. Keep existing Supabase URL/key settings.
5. **Vercel → Project → Settings → Environment Variables → Production:** add `SOCIAL_DATABASE_READY=true` and `SOCIAL_TOKEN_ENCRYPTION_KEY` as a Secret. The encryption key must be 64 random hexadecimal characters generated by a trusted password manager. Keep a secure backup. Do not put its value in chat or GitHub. Add the relevant provider credentials from the preceding/following steps as Secrets. Keep the now-working `TAROT_SITE_URL=https://www.thedivinework.com` unchanged; use the exact `www` callback URLs. Redeploy after saving configuration.
6. **TikTok:** open https://developers.tiktok.com/, create/select an app, configure the web **Login Kit** and add redirect `https://www.thedivinework.com/api/studio/social/tiktok/callback`. Request `user.info.basic` and `user.info.profile` so the code can verify the exact `divinework.store` username. Add `TIKTOK_CLIENT_KEY` and `TIKTOK_CLIENT_SECRET` in Vercel. Use sandbox/authorized test accounts where available until TikTok approves live access. TikTok may require app/domain verification, privacy policy, a screencast or app review. No `video.publish` permission is requested; future automatic posting requires Content Posting API implementation and its audit/permissions.
7. **YouTube:** open https://console.cloud.google.com/, create/select a project and enable **YouTube Data API v3**. In **Google Auth Platform** configure Branding/Audience/Data access, include the owner as a test user while the app is Testing, and add scope `https://www.googleapis.com/auth/youtube.readonly`. In Clients create an OAuth client of type **Web application** with redirect `https://www.thedivinework.com/api/studio/social/youtube/callback`. Add `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in Vercel. Select the Google/Brand Account channel whose handle is `@divine-work`; a different channel is rejected. Google may require verification for production access. No `youtube.upload` scope is requested; future Shorts uploads require separate code, consent and potentially Google audit requirements.
8. Use `https://www.thedivinework.com/social-data-privacy` as the integration privacy/deletion-instructions URL in the developer applications where suitable. Confirm the providers' current review/domain/business requirements; those external approvals are not demonstrated by mocked tests. Do not use the Instagram signed-request deletion callback for a separate Facebook app secret. This phase provides owner-operated deletion instructions for the new three platforms, not provider revocation webhooks.
9. Open `https://www.thedivinework.com/studio/social`, sign in with the existing Studio credentials and click one configured platform's **Conectează** button. Authorize the correct account in the provider's official login and return to Studio. Confirm the returned account/channel/Page identity and expiry. An unconfigured or failed OAuth flow must not be treated as connected. Do not share callback URLs containing temporary authorization codes.

## Security and limits

OAuth states are random, provider-bound, hashed in Postgres, ten-minute and single-use; HttpOnly, SameSite=Lax cookies bind the redirect to the initiating browser (Secure in production). Google/TikTok use PKCE with an encrypted server-side verifier. All token exchanges and API identity reads happen server-side at fixed HTTPS hosts with timeouts and redirect rejection. Tokens (including Google/TikTok refresh tokens) are AES-256-GCM encrypted with a separate server key. Only safe identifiers/status/expiry are returned to the owner UI. Provider error bodies are not echoed or logged by application code. Facebook token exchanges use form POST rather than putting app secrets in request URLs.

Facebook account matching uses the owner's configured numeric Page ID because a vanity handle is not a reliable Graph API identity field. TikTok and YouTube validate the requested exact handle. Facebook stores the Page token with a conservative expiry bounded by the originating long-lived user token; it does not promise permanent validity. There is no background refresh worker for these three providers in this connection-only phase. Tokens are retained encrypted until local disconnection; refresh tokens are reserved for future authorized adapters. Expiry requires reconnection in the current UI. Google Testing apps may expire refresh tokens after seven days; provider revocations may take effect before the displayed expiry. Stored authorization is not continuous proof of live connectivity.

**Elimină conexiunea locală** removes stored connection credentials and pending OAuth states. It does not revoke the provider-side grant; use the provider's connected-app settings as well. No existing posts are deleted. Tests mock provider responses; a real grant and later separately authorized publishing test remain outstanding.
